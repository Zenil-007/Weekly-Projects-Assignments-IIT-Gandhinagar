# Northwind Support Copilot
**Futurense AI Clinic — Week 15 & Week 16**

A RAG-based support copilot built for Northwind, a mid-size B2B SaaS company. Support agents waste hours searching scattered help docs, changelogs, and policy PDFs. This system retrieves the right document, answers with inline citations, and is measurably trustworthy — not just demo-ready.

## Quickstart

### 1. Install dependencies

```bash
pip install -r requirements.txt
```

### 2. Set environment variables

```bash
export OPENAI_API_KEY=sk-...

# Optional — Langfuse tracing (Week 16). Skip if you don't have an account.
export LANGFUSE_PUBLIC_KEY=pk-lf-...
export LANGFUSE_SECRET_KEY=sk-lf-...
export LANGFUSE_HOST=https://cloud.langfuse.com   # default
```

### 3. Add your documents

Drop `.txt` or `.md` support documents into the `docs/` folder. Both scripts fall back to a built-in 8-document synthetic Northwind corpus if `docs/` is empty — useful for a quick end-to-end demo.

### 4. Run Week 15 — De-risk Spike

```bash
python week15_derisk_spike.py
```

Outputs a hit-rate table to the console and writes `findings/FINDINGS.md`.

### 5. Run Week 16 — Evaluable Core

```bash
python week16_evaluable_core.py
```

Runs the full pipeline, prints a Ragas scorecard, runs 2 improvement experiments, and writes results to `observability/`.

## Week 15 — Spec & De-risk

### What it does

| Step | Description |
|------|-------------|
| Load | Reads `.txt` / `.md` files from `docs/` |
| Chunk | Applies two strategies: **Fixed 512-token** and **Recursive/Semantic** |
| Embed | `text-embedding-3-small` via OpenAI API |
| Store | In-memory Chroma vector store |
| Evaluate | 10 representative questions → hit-rate table (Y/N per question) |
| Report | Writes `findings/FINDINGS.md` with verdict and miss analysis |

### Chunking strategies compared

**Fixed 512-token** — splits on word count regardless of sentence or paragraph boundaries. Fast, predictable, but leaves answers split across chunk edges.

**Recursive/Semantic** — splits on paragraph boundaries first, then sentence boundaries. Keeps semantically coherent passages together. Consistently higher hit-rate on real, messy documents.

## Week 16 — Build the Evaluable Core

### Pipeline architecture

```
User Question
     │
     ▼
[ Embed question ]  ──── text-embedding-3-small
     │
     ▼
[ Chroma retriever ]  ── top-k chunks (default k=3)
     │
     ▼
[ Prompt assembly ]  ─── system prompt + context block with [source: filename] tags
     │
     ▼
[ LLM generation ]  ──── gpt-4o-mini, temperature=0
     │
     ▼
[ Answer + citations ]
```

Every step is wrapped with Langfuse `@observe()` — producing a structured trace with retrieval sources, token counts, latency, and estimated cost per query.

### Golden evaluation set

30 hand-verified Q&A pairs across four flavours:

| Flavour | Count | Purpose |
|---------|-------|---------|
| Easy | 15 | Single-document lookups |
| Ambiguous | 5 | Multiple plausible interpretations |
| Multi-hop | 5 | Requires synthesising two documents |
| Adversarial | 5 | Answer not in corpus — system must abstain |

### KPI targets & do-not-ship floors

| Metric | Target | Do-Not-Ship Floor | What it measures |
|--------|--------|-------------------|-----------------|
| Faithfulness | ≥ 0.90 | < 0.70 | Every claim traces to retrieved context |
| Answer Relevancy | ≥ 0.80 | < 0.70 | Answer addresses the question asked |
| Context Precision | ≥ 0.70 | < 0.60 | Retrieved chunks are relevant and well-ordered |
| Context Recall | ≥ 0.80 | < 0.60 | Retrieved context contains the answer |
| p95 Latency | ≤ 3 s | > 8 s | End-to-end response time |
| Cost / Query | ≤ $0.01 | > $0.05 | Tokens × price |

### Improvement experiments

Each experiment changes exactly one variable and re-measures on the identical golden set:

| Experiment | Variable | Typical Delta |
|------------|----------|---------------|
| Top-k: 3 → 5 | `k` in retriever | Context recall +0.06, faithfulness ±0.00 |
| Chunk size: 1200 → 600 chars | `max_chars` in chunker | Context precision +0.08, answer relevancy −0.03 |

The kept configuration is committed as the new baseline.

### LLM diagnostic gate

The worst-scoring question triggers an automated diagnostic:

1. Failing case (question + retrieved context + bad answer + scores) is submitted to the LLM
2. LLM classifies root cause: **retrieval failure** vs **generation failure**
3. LLM proposes a concrete fix
4. Human critique is appended
5. Fix is applied and re-measured — a diagnosis without re-measurement fails the gate

## Engineering lessons

**Week 15**
- Define measurable KPIs with do-not-ship floors *before* writing code — prevents the "looks good in demo" failure mode
- Typed data contracts (Pydantic / dataclasses) eliminate pipeline ambiguity at component boundaries
- Recursive/semantic chunking consistently outperforms fixed-size chunking on real, messy documents
- A spike that fails early is cheaper than a demo that fails in front of stakeholders

**Week 16**
- Retrieval is the biggest lever — changes to top-k, chunk size, and reranking move metrics more than prompt tuning
- Never report a single metric: context precision can look healthy while context recall is low
- Langfuse traces turn "the answer was wrong" into "retrieved chunks 2 and 4 were off-topic" — root cause in seconds
- Adversarial cases expose overconfidence — measuring abstention correctness is not optional for production
- The do-not-ship floors from Week 15 become the reality check for Week 16 architecture decisions

## Observability

When Langfuse keys are configured, every pipeline run produces a structured trace viewable at [cloud.langfuse.com](https://cloud.langfuse.com):

- **Retrieve step** — question, top-k sources, distances
- **Generate step** — full prompt, answer, token count
- **Trace level** — total latency, estimated cost, tags

Screenshots of the dashboard and a single trace are committed to `/observability/`.
